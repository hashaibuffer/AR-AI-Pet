## 一、项目全貌

### 产品定位

"屿见/桌屿"是一个**单用户单宠物**的 AR AI 伙伴系统，由四层组成：

| 层 | 硬件/载体 | 角色 |
|---|---|---|
| AR 眼镜 | XREAL + Beam Pro | Unity 中枢，虚实融合显示 |
| 实体机器人 | StackChan（ESP32 桌面机器人） | 语音交互、头部动作、底座移动 |
| 运动底座 | NanoDrive（Arduino Nano + A4950） | 双轮差速移动、编码器反馈、看门狗安全 |
| 后端服务 | 本地部署 | Agent Runtime + PostgreSQL + Mem0/Qdrant + MCP Hub |

### 技术架构（当前正式基线）

```
XREAL 眼镜 ↔ Beam Pro (Unity 中枢)
                    ↕ WebSocket
           ar-aipet-server (统一入口 :8090)
          /        |         |         \
    Agent Runtime  数据服务   MCP Hub    设备会话
    (文字主Agent)  (PostgreSQL) (语义工具)  (/ws/device)
         |              |          |           |
    Mem0/Qdrant    业务唯一事实   23个工具   StackChan Adapter
    (长期记忆)     (10张表)                 → BLE → NanoDrive
```

### 内容体系

三人格（温柔陪伴/活力搭档/嘴硬心软），两款游戏：

- **六面星河**：五骰子酒馆骰子，双方各 11 回合每回合最多 3 投，11 个计分格
- **一寸春**：回合制农场，一季 14 回合，机器人有自己 2×2 小田可自主照料

内容遵循"设计 Markdown → runtime JSON → 代码只读"的权威链，Agent 不改规则不伪造事实。

### 团队分工

- **A**：XR 客户端（Unity/XREAL/Beam Pro）
- **B**：AgentOS/StackChan/NanoDrive（项目主责）
- **C**：游戏/规则/内容/美术/比赛

## 四、优化方向

### A. 架构与工程化

**A1. 数据库迁移管理** — 当前最大工程化缺口。10 张表的 DDL 隐式散落在 `db.py`/`farm.py`/`maintenance.py`/`server.py` 的裸 SQL 中，`seed_defaults()` 假设表已存在。应创建 Alembic 迁移脚本和版本管理，使 `docker compose up` 能从零初始化完整数据库。

**A2. 文档收敛** — 当前有 4 份 A 视角操作指南（`A-两周开发计划`、`A-开发计划-两周详细`、`A-每日操作步骤指南`、`A-详细操作步骤指南`）内容高度重叠，且路径不一致（`D:/AR-AI-Pet` vs `C:\Users\Administrator\AR-AI-Pet` vs 实际 `D:\projects\AR-AIPet`）。应合并为一份权威指南，其余归档。

**A3. MCP 架构合并落地** — traz 事件已确认"项目侧 MCP 与 Robot Bridge 可合并，设备固件 MCP 保留"的结论，但 17 个文件的改动是否已提交需确认。应确保合并后的 `ar-aipet-server` 单一入口不改变数据库/游戏规则/Mem0 职责边界。

### B. 功能补全

**B1. 真实 StackChan Adapter 端到端验证** — 当前最高优先级。StackChan 已连 WiFi 和 BLE，但完整链路"Agent → Robot Bridge → StackChan WebSocket Adapter → StackChan → BLE → NanoDrive"尚未跑通。需要：建立动作网关会话、验证 play_motion/set_head_angles/base_move/stop 通过完整链路到达实体、验证状态回传。

**B2. 语音上行链路** — `VoiceClient.cs` 当前是骨架，`SimulateAgentResponse` 模拟回复。需要接入真实 STT（语音转文字发送给 Agent）和 TTS（Agent 文字回复转语音播放）。StackChan 侧 Xiaozhi 语音会话已通过验证，但 Unity 侧 PC 语音通道未接入。

**B3. 真机设备 Transport** — `DeviceConnectionManager.cs` 真机分支被注释，始终回退 Mock。Beam Pro 到货后需实现真实 XREAL/StackChan `IDeviceTransport`。

**B4. 真实 Mem0/Qdrant 验收** — Mock 链路通过，但真实 LLM/Embedding 凭据未配置。需要配置真实 API Key，验证长期记忆写入/检索/去重/重试全链路。

### C. 游戏与 UI

**C1. Unity 游戏 UI 落地** — `桌屿游戏-Unity实现文档.md` 提供了完整蓝图和 C# 代码（六面星河计分表、一寸春农场 UI、桌屿主岛导航），但 5 天创建清单全部未勾选。`YahtzeeGame.cs`（461 行）和 `FarmingGame.cs` 已有核心逻辑，但 UI 层（GameObject 层级、RectTransform、配色）尚未搭建。

**C2. 屿见 APP UI 落地** — `屿见APP-设计文档.md` 提供了完整设计系统（色板、组件、6 个页面）和 6 天 Unity 落地指南，但文档未标注实现进度，推测为起始阶段。

### D. 测试与验收

**D1. 完整端到端闭环** — 文档 `07-测试与Demo验收.md` 明确要求验证"完整 AR→Agent→机器人端到端闭环"和"完整 Demo 连续运行三次"，目前均未完成。

**D2. 比赛材料** — `competition/README.md` 指出当前无已验收正式比赛材料。需要：Demo 脚本（演示顺序/设备/降级方式）、PPT、视频分镜、Demo 视频。规则明确"未验证能力不得写入成片或现场承诺"。

## 六、风险提示

1. **Beam Pro 到货时间**是 A 侧最大不确定因素。A 视角计划已准备 PC 降级方案（第一周全 PC Play Mode），但 Day8-10 的真机联调和 APK 构建依赖到货。
2. **路径不一致**可能导致 A 侧执行操作指南时出错，需优先校正。
3. **语音方案分歧**：文档说"语音网关不在本轮"，但 StackChan 侧 Xiaozhi 语音已验证。需明确演示时用哪条语音通道——StackChan 侧 Xiaozhi 还是 Unity 侧 PC 麦克风。
4. **比赛材料为零**且规则严格（"未验证能力不得写入成片"），需在端到端闭环跑通后立即启动材料制作，预留足够时间。
5. **数据库无迁移管理**在当前 Mock/开发阶段可容忍，但首次演示前应补齐，避免演示环境从零搭建时表不存在。
