# 动作网关会话恢复步骤

> 本文档是硬件侧操作手册。标记 **HUMAN/HARDWARE** 的步骤必须在现场由人执行，软件侧无法替代。

## 背景与根因

StackChan 实体无法建立动作网关会话，有**三层叠加原因**：

1. **Wi-Fi 未连接**（HARDWARE）：2026-08-13 COM7 探测显示 `Haven't to connect to a suitable AP now!`，设备未获得 IP。
2. **AI.AGENT 应用未打开**（HARDWARE）：Mooncake 固件只在 AI.AGENT 应用 `onOpen()` 回调中调用 `requestXiaozhiStart()`；`McpActionClient::start()` 在 Xiaozhi 就绪后才被调用。**Wi-Fi 已连接但 AI.AGENT 未打开时，动作网关无设备会话属于预期行为，不是端口故障。**
3. **固件动作网关 URL 不匹配**（SOFTWARE，已诊断）：最后一次构建的固件配置为 `CONFIG_STACKCHAN_MCP_ACTION_GATEWAY_URL="ws://192.168.50.133:8765"`（Scheme B 端口 8765，无路径），但当前统一服务监听在 `ws://<PC_IP>:8090/ws/device`（端口 8090，路径 `/ws/device`）。端口、路径和可能的 IP 都不匹配。

## 连接方向说明

当前统一服务架构是**设备主动连接**（device-initiated）：

```text
StackChan 固件 McpActionClient
  → WebSocket 连接
  → ws://<PC_IP>:8090/ws/device
  → 统一服务 DeviceSessionManager
  → Agent 发起 robot.action.request
  → 通过同一 WebSocket 下发到设备
```

这和 Scheme B 的 `8765`（设备→网关）与 `8767`（项目→网关）是不同入口，证据不能互相迁移。

## 恢复步骤

### 步骤 1：确认 PC 局域网 IP（HUMAN/HARDWARE）

在运行统一服务的 Windows 电脑上执行：

```powershell
# 在 PowerShell 中运行
Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.InterfaceAlias -notmatch "vEthernet|Loopback" -and $_.PrefixOrigin -eq "Dhcp" } | Select-Object -First 1 -ExpandProperty IPAddress
```

记下这个 IP（例如 `192.168.50.133`）。后续步骤中的 `<PC_IP>` 都替换为这个值。

### 步骤 2：启动统一服务

```powershell
cd D:\projects\AR-AIPet\services\agent-service
docker compose --profile unified up --build -d
```

等待健康检查通过：

```powershell
# 应返回 {"status":"ok",...}
Invoke-RestMethod -Uri "http://localhost:8090/health" -TimeoutSec 3
```

### 步骤 3：确认设备端点和固件 URL 匹配（SOFTWARE）

设备应连接的 URL 为：

```
ws://<PC_IP>:8090/ws/device
```

当前固件构建中写死的是 `ws://192.168.50.133:8765`。如果 `<PC_IP>` 不是 `192.168.50.133`，或端口/路径不匹配，则**必须修正固件配置**。修正方式二选一：

#### 方式 A：重新构建固件（推荐，HARDWARE）

在 ESP-IDF v5.5.4 PowerShell 中，使用 stackchan-mcp 构建脚本注入正确 URL：

```powershell
# 在仓库根目录执行
.\firmware\stackchan-mcp\scripts\build-accepted-baseline.ps1 `
  -GatewayUrl "ws://<PC_IP>:8090/ws/device"
```

构建完成后烧录：

```powershell
# 在 ESP-IDF PowerShell 中
cd firmware\stackchan-mcp\upstream\firmware
idf.py -p COM7 flash
```

#### 方式 B：通过 gateway_config_set 临时修改（HARDWARE）

如果固件已支持 `gateway_config_set` MCP 工具，可通过 Scheme B 网关临时修改 `fallback_url`：

```python
# 需要本地 stackchan-mcp 网关运行在 8765
# python firmware/stackchan-mcp/artifacts/gateway_config_set_once.py
# 修改 fallback_url 为 ws://<PC_IP>:8090/ws/device
```

注意：`gateway_config_set` 只用于首次部署、更换网关或故障恢复，不应用于普通交互。

### 步骤 4：确认 StackChan 与 PC 在同一 2.4 GHz Wi-Fi（HUMAN/HARDWARE）

- StackChan 的 ESP32-S3 只支持 2.4 GHz Wi-Fi。
- 确认 PC 和 StackChan 连接到同一个 SSID。
- 如果 PC 使用 5 GHz，需要确认路由器是否做了双频合一（可能导致设备无法发现彼此）。

### 步骤 5：打开 AI.AGENT 应用（HUMAN/HARDWARE）

**这是最关键的手动步骤。**

当前刷入的 Mooncake 固件采用应用中心架构。`McpActionClient::start()` 由 `_stackchan_update_task` 在 Xiaozhi 就绪后调用。只有 AI.AGENT 应用的 `onOpen()` 才会调用 `requestXiaozhiStart()`，之后才会启动 Xiaozhi 语音 WebSocket 和动作 MCP WebSocket。

- 在 StackChan 屏幕上打开 AI.AGENT 应用。
- 如果设备配置了开机自启 AI.AGENT，确认自启已生效。
- **Wi-Fi 已连接但 AI.AGENT 未打开时，动作网关没有设备会话是预期现象，不应误判为 Wi-Fi、BLE 或端口故障。**

### 步骤 6：验证设备会话已建立（HUMAN/HARDWARE）

复位 StackChan，然后运行串口诊断脚本：

```powershell
cd D:\projects\AR-AIPet\services\agent-service
powershell -ExecutionPolicy Bypass -File .\check_com7.ps1
```

在 COM7 串口输出中应看到：

```
got ip: <设备IP>                        # Wi-Fi 已连接
connecting action gateway: ws://<PC_IP>:8090/ws/device  # 固件 URL 匹配
action gateway connected, session=...   # 会话已建立
```

如果看到 `CONFIG MISMATCH`，返回步骤 3。

也可以检查服务端是否注册了设备会话：

```powershell
Invoke-RestMethod -Uri "http://localhost:8090/health/device" -TimeoutSec 3
# 应返回 sessionCount >= 1
```

### 步骤 7：运行统一冒烟测试

```bash
cd D:\projects\AR-AIPet\services\agent-service
python scripts/unified_smoke.py
```

期望输出 `UNIFIED_SMOKE_OK`。如果失败，脚本会打印阶段追踪表，指出具体在哪一步断开。

### 步骤 8：验证 Agent 动作到达实体（HUMAN/HARDWARE）

```powershell
# 通过 MCP 发送测试动作
$body = @{ jsonrpc = "2.0"; id = 1; method = "tools/call"; params = @{ name = "robot.react"; arguments = @{ intent = "wave"; parameters = @{ motion = "happy" } } } } | ConvertTo-Json -Depth 5
Invoke-RestMethod -Uri "http://localhost:8090/mcp" -Method Post -Body $body -ContentType "application/json" -TimeoutSec 10
```

应看到 StackChan 执行 `happy` 动作。确认后，动作网关会话恢复完成。

## 成对记录要求

每次现场联调必须记录以下五项配对数据，缺一不可：

| 项目 | 值 |
|---|---|
| 设备 IP | （COM7 日志中的 `got ip` 值） |
| PC IP | （步骤 1 中检测的 LAN IP） |
| 固件动作网关 URL | （COM7 日志中的 `connecting action gateway` 值） |
| 8090/8765/8767 监听 | （PC 端监听确认） |
| 网关设备会话 | （`/health/device` 返回或 COM7 日志中的 `connected`） |

若设备仍指向旧 PC 地址，先修正固件配置或刷入匹配配置，再验证 Agent 动作。

## 常见误判

| 现象 | 误判 | 正确解释 |
|---|---|---|
| Wi-Fi 已连接但网关无会话 | "端口故障" | AI.AGENT 应用未打开；Mooncake 需 `onOpen()` 触发 `requestXiaozhiStart()` |
| 设备日志有 `8765` | "网关已监听" | `8765` 是 Scheme B 端口；当前统一服务在 `8090/ws/device` |
| COM7 显示 `base_move` 工具 | "官方 Mooncake 已支持底座" | `base_move`/`base_stop` 不在官方锁定源码中，只在 Scheme B 参考源码中 |
| 8080/ws 连通 | "动作网关已通" | 8080/ws 是直接设备路径，与 8765/8090 连接方向不同，证据不能迁移 |
