## 单人游戏边界

- 快艇骰子：用户与宠物对战。游戏系统负责固定规则、合法操作和计分；宠物参与游戏、回应结果和陪伴互动。
- 种菜：用户与宠物共同经营。用户和宠物共同完成种植、照料和收获；游戏系统负责状态推进和结果计算。
- 单人游戏不设额外裁判、NPC 或任务发布角色。使用“游戏伙伴”“互动台词”“引导与反馈”。
- Agent 或宠物不能改变固定规则和游戏结果。多人聚会可保留聚会引导，但不与单人游戏混写。
- 具体规则由 C 定义；A、B 确认可实现性后冻结。

当前首版内容基线已经写入 `content/design/` 与 `content/runtime/`，供 Agent Mock 和 Unity 接入直接使用；C 后续可在不改变稳定 ID 和规则边界的前提下继续修订。

## 执行补充

- 从 Day 2 起每天完成一次最小端到端联调，并把问题写入验收文档。
- A、B必须维护各自依赖的 Mock。真实设备或对方模块未完成时，使用同一协议继续开发。
- 当前阶段依赖的规则和接口应在前一阶段完成确认；未确认项不得由使用方自行补定义。
- Day 8用于冻结后的综合测试，不是第一次完整联调。
- NanoDrive 的实机接入截止点为 Day 7 结束。超时则使用 Mock 或固定底座降级演示，不阻塞 AR 与 StackChan 主体 Demo。
- 每个阶段产生的代码、协议、Mock和对应文档通过同一个 PR 交付。

## 必须共同遵守的约束

1. **主责人定义，参与者确认。**接口、规则或表现由对应主责人提出，受影响的人确认后再冻结。
2. **一个内容只有一个正式来源。**其他位置只引用，不重复维护。
3. **规则由C主责。**开发不能在代码中私自改变玩法、数值和互动内容。
4. **接口确认后再接入。**接口变化由主责人更新，参与者确认影响后执行。
5. **验证结果如实记录。**没有实际运行的能力标记为待验证。
6. **文档与开发同步。**影响他人的变化在当天更新。
7. **源文件与程序文件分开。**C维护内容源文件，A、B负责接入各自工程。
8. **实现方式由负责人决定。**计划只约束交付结果、接口和依赖，不限定负责人职责范围内的具体实现。
