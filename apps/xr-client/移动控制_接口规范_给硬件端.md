# Stack-chan 移动控制 · 接口规范

> **文档目的**：定义 Unity 游戏端（我方）和 Stack-chan 移动底座（b 方负责）之间的通信接口。
> **给谁看**：b（移动底座固件开发）。
> **版本**：v1.0 · 2026-08-05

---

## 一、通信方式

| 项目 | 规格 |
|------|------|
| 协议 | WebSocket（和现有表情通信共用同一条连接） |
| 数据格式 | JSON 文本帧 |
| 连接方向 | Unity → Stack-chan（Unity 是 Client，Stack-chan 开 WebSocket Server） |
| 地址 | `ws://<stack-chan-ip>:<port>/device`（和现有 `DeviceClient.cs` 用的同一个连接） |

> **关键点**：移动指令和表情指令**共用同一条 WebSocket 连接**，不要单独开连接。通过 JSON 里的 `type` 字段区分消息类型。

## 二、坐标系定义

桌面俯视图，俯视看下去：

```
         +Y (远 / 桌子后方)
          |
          |
 -X ------+------+ +X (右)
          |
          |
         -Y (近 / 靠近用户)
```

| 参数 | 定义 |
|------|------|
| 原点 (0,0) | 桌面中心点（开机标定时确定） |
| X 轴 | 水平方向，+X = 向右 |
| Y 轴 | 纵深方向，+Y = 向远（桌子后方） |
| 单位 | **米**（和 Unity 一致），桌面游戏范围通常 -0.4 ~ +0.4 |
| 朝向 angle | 弧度，0 = 面向 +Y（桌子后方），逆时针为正 |

> **为什么用米？** Unity 默认单位就是米。AR 虚拟菜地坐标直接发给机器人就能用，不需要换算。

## 三、Unity → Stack-chan：移动指令（共 3 条）

### 3.1 移动到目标点

```json
{
  "version": "0.1",
  "messageId": "evt-xxxxxxxx",
  "timestamp": "2026-08-05T10:00:00Z",
  "source": "xr-client",
  "type": "pet.move",
  "payload": "{\"x\": 0.3, \"y\": -0.2, \"angle\": 1.57, \"speed\": 0.5}"
}
```

**payload 字段**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `x` | float | 是 | 目标点 X 坐标（米） |
| `y` | float | 是 | 目标点 Y 坐标（米） |
| `angle` | float | 否 | 到达后的目标朝向（弧度）。不传 = 不改变朝向 |
| `speed` | float | 否 | 移动速度 0.0~1.0，1.0 = 最大速度。默认 0.5 |

**b 需要做的**：
1. 解析 `x, y` 目标坐标
2. 规划路径（直线即可，桌面范围小不需要避障）
3. 控制底盘电机移动到目标点
4. 到达后回传 `pet.move.arrived`（见第四节）

### 3.2 紧急停止

```json
{
  "type": "pet.move.stop",
  "payload": "{\"reason\": \"user_command\"}"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `reason` | string | 停止原因：`user_command`（用户操作）/ `safety`（安全触发）/ `game_pause`（暂停游戏） |

**b 需要做的**：立即停止电机，不管当前在做什么。收到这条消息后机器人必须 **0.1 秒内** 完全停止。

### 3.3 归位（回到桌面中心）

```json
{
  "type": "pet.move.home",
  "payload": "{\"speed\": 0.3}"
}
```

**b 需要做的**：移动到坐标系原点 (0, 0)，朝向默认方向（+Y）。游戏退出 / 回到主菜单时 Unity 会发这条。

## 四、Stack-chan → Unity：位置反馈（共 3 条）

### 4.1 到达通知

```json
{
  "type": "pet.move.arrived",
  "payload": "{\"x\": 0.3, \"y\": -0.2, \"angle\": 1.57, \"success\": true}"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `x, y` | float | 实际到达位置 |
| `angle` | float | 实际到达朝向 |
| `success` | bool | true = 正常到达，false = 被障碍挡住/超时/安全停止未到达 |

**Unity 收到后**：触发 AR 表情（到达 → happy），如果 `success=false` 则显示提示。

### 4.2 位置上报（高频，20Hz）

```json
{
  "type": "pet.pose.report",
  "payload": "{\"x\": 0.15, \"y\": 0.08, \"angle\": 0.78, \"battery\": 87}"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `x, y` | float | 当前实时位置（米） |
| `angle` | float | 当前朝向（弧度） |
| `battery` | int | 电量百分比 0-100（选填） |

**频率**：每 50ms 上报一次（20Hz）。

**这是最关键的一条**——Unity 靠这个数据实时更新 AR 里 Stack-chan 的位置。如果这数据断了或延迟太大，AR 里的虚拟形象就会和实体机器人错位。

**b 需要保证**：
- 位置精度至少 ±2cm
- 上报延迟 < 100ms（从传感器采样到 WebSocket 发出）
- 通信断开时底盘自动停止（安全保护）

### 4.3 移动失败通知

```json
{
  "type": "pet.move.failed",
  "payload": "{\"reason\": \"obstacle\", \"x\": 0.1, \"y\": 0.0}"
}
```

| reason 值 | 含义 |
|-----------|------|
| `obstacle` | 遇到障碍物 |
| `edge_detected` | 检测到桌面边缘（防跌落触发） |
| `timeout` | 移动超时（5 秒未到达） |
| `motor_error` | 电机故障 |
| `low_battery` | 电量不足（<10%） |

## 五、完整消息流示例

### 场景：用户在 AR 里点击"去菜地"，Stack-chan 走过去

```
时间线    方向              消息
─────────────────────────────────────────────────────
T+0ms     Unity → SC       pet.move  {x:0.3, y:0.1, speed:0.5}
T+50ms    SC → Unity       pet.pose.report  {x:0.02, y:0.01, angle:0.5}
T+100ms   SC → Unity       pet.pose.report  {x:0.05, y:0.02, angle:0.6}
T+150ms   SC → Unity       pet.pose.report  {x:0.09, y:0.04, angle:0.7}
  ...      ...              （每 50ms 上报一次）
T+2000ms  SC → Unity       pet.pose.report  {x:0.30, y:0.10, angle:0.78}
T+2050ms  SC → Unity       pet.move.arrived {x:0.30, y:0.10, success:true}
```

### 场景：Stack-chan 快走到桌子边缘，防跌落触发

```
T+0ms     Unity → SC       pet.move  {x:0.4, y:0.35}
T+1500ms  SC → Unity       pet.pose.report  {x:0.38, y:0.33}
T+1550ms  SC → Unity       pet.move.failed  {reason:"edge_detected", x:0.38, y:0.33}
                          ↑ b 的固件检测到边缘，主动停止并上报
T+1560ms  Unity → Unity    AR 显示提示："哎呀！差点掉下去了！"
T+1560ms  Unity → SC       pet.expression  {emotion:"surprised", intensity:1.0}
```

## 六、防跌落安全约定

**这是安全红线。双方都要实现保护：**

| 保护层 | 谁负责 | 做什么 |
|--------|--------|--------|
| 硬件层 | b | 底座红外/超声波检测桌面边缘 → 立即停止 |
| 固件层 | b | 收到 `pet.move.stop` 后 0.1s 内停止 |
| 软件层 | Unity | 发送移动指令前检查目标点是否在安全围栏内 |
| 通信层 | 双方 | 位置上报中断超过 0.5s → 底盘自动停止 |

> **原则**：宁可误停（以为要掉了其实没事），不能不停（真掉了）。

## 七、Mock 模式（b 没开发完时 Unity 怎么测）

Unity 端实现了 Mock 模式：当 `ModeConfig.UseMock = true` 时，不连真实 Stack-chan，而是用本地脚本**模拟**移动和位置上报。

b 不需要关心 Mock 模式——这是 Unity 端自己用的。但建议 b 在开发固件时也写一个类似的 Mock，先对着 Postman / wscat 测 WebSocket 消息收发，再接真实电机。

## 八、联调 Checklist

双方各自开发完后，按这个清单联调：

- [ ] wscat 能连上 Stack-chan 的 WebSocket Server
- [ ] 发 `pet.move` → Stack-chan 真的动了
- [ ] Stack-chan 持续上报 `pet.pose.report`（用串口监视器看频率）
- [ ] 发 `pet.move.stop` → 0.1s 内停住
- [ ] 手把 Stack-chan 推到桌边 → 自动停止 + 上报 `pet.move.failed`
- [ ] Unity AR 里看到的 Stack-chan 位置和实际位置误差 < 3cm
- [ ] 连续跑 10 分钟，WebSocket 不掉线
- [ ] 断开 WiFi → 底盘自动停止

## 九、附录：消息类型速查

| 方向 | type | 说明 |
|------|------|------|
| Unity → SC | `pet.move` | 移动到目标点 |
| Unity → SC | `pet.move.stop` | 紧急停止 |
| Unity → SC | `pet.move.home` | 回到中心点 |
| SC → Unity | `pet.move.arrived` | 到达通知 |
| SC → Unity | `pet.pose.report` | 位置上报（20Hz） |
| SC → Unity | `pet.move.failed` | 移动失败 |
| Unity → SC | `pet.expression` | 表情指令（已有，共用连接） |
| SC → Unity | `pet.state.changed` | 状态变化（已有，共用连接） |

> **已有的表情/语音消息继续走这条连接，不冲突。**
